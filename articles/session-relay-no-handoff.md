## 止まった画面のスクショを貼ると、続きが始まる

夜、AIと作業していると「利用制限に達しました。しばらくしてからもう一度お試しください」と出ることがあります。数時間待てば戻ります。でも、いま進めたい。そこで別のAIに頼むことになりますが、そのチャットは前の話を知りません。だから毎回、一から説明することになります。

いまの私はこうしています。止まった画面のスクショを撮って、**別のAIツール**の新しいチャットに貼って、「止まったので続きから」と打つ。それだけです。利用枠はツールごとに別なので、Claudeが止まってもCodexは動きます。新しいAIが前の会話を自分で読みに行って、途中から作業が再開されます。引き継ぎの説明は1行も書きません。数時間後に枠が戻って同じツールで続ける場合も、やることは同じです。

この記事は、それをやるために作った session-relay という道具の話です。昨日はスマホのClaudeで考えたことをMacに届けるところまで繋がったので、そこまで書きます。

https://github.com/shoujiki-panman/session-relay

## こんな人のための道具です

- 利用枠やチャットの長さで、AIとの会話がよく止まる
- ClaudeとCodexのように、複数のAIツールを行き来している
- スマホのClaudeで考えごとをして、続きはMacでやりたい
- 止まるたびに「いまの状況をまとめて」と引き継ぎ書を書かせるのに疲れた

私は全部に当てはまります。

## 困っていたこと

止まるたびに、私は引き継ぎ書を書いていました。「ここまで進んでいて、次はこれをやる。この判断はこういう理由で」。outputsフォルダには handoff-なんとか.md が17本たまっています。書くのに毎回10分か20分。しかも次のチャットがそれをちゃんと読んでくれるとは限らない。

ある日、引き継ぎ書がどれくらい壊れているか実測してみました。事実は11項目中8項目残っていました。悪くない数字です。でも落ちていたのは私の発言の原文でした。何に苛立って、何を却下して、どんな言い方で決めたのか。要約はそこを丸めます。丸められた側のAIは、私が一度捨てた案を平気でもう一度持ってきます。

もうひとつ数字があります。あるセッションの記録は13MBありました。そのうち人間の発話、つまり私がキーボードで打った文章は11.8KB。全体の0.09%です。AIの長い返答とツールの実行ログが残りの99.91%を占めていました。

だったら、その0.09%だけを原文のまま運べばいい。引き継ぎ書はもう書かない。そう決めて作り始めました。

## 仕組み

Claude CodeもCodexも、会話の記録を手元のMacにJSONLで残しています。relayはそれを直接読んで、人間の発話だけを時系列で全件抜き出します。要約はしません。新しいセッションは、私が実際に打った言葉の全文と、直近の経過、触ったファイル、gitの状態を受け取って始まります。

コマンドもあります。

```sh
relay              # いまの会話を新しいセッションで開く
relay --to codex   # Codexで開く
relay --pick       # 一覧から選ぶ
```

中身は3つに分かれていて、**全部を使う必要はありません**。

1. **relayコマンド** — 会話を別のスレッドや別のAIで開く本体。これだけでも引き継ぎはできます
2. **MCPサーバー＋スキル** — 「続きから」と言うだけでAIが自分で会話を取りに来るようにする層。`relay install` で入ります
3. **スマホの投函口** — スマホのClaudeの会話をMacへ預ける口。Cloudflareの設定が要るので、欲しくなった人だけ

ほとんどの人は1と2だけで足ります。

ただ、ふだん使うのはコマンドではありません。MCPサーバーにしてあるので、新しいチャットに「続きから」とか「キャンバスの話の続き」と言うだけで、AIが自分で前の会話を取りに来ます。冒頭のスクショ貼りも同じで、画像から「どの会話の続きか」をAIが判断して、relayで原文を引きます。候補が複数あるときは一覧を見せて選ばせます。

効果は実測してあります。文脈ゼロの新しいセッションに17KBの抽出結果だけを渡したら、プロジェクトの全体像だけでなく、前のアプリを中止した理由を私の発言の原文つきで答えました。未回答の質問が残っていることまで指摘してきたのは、ちょっと悔しかったです。

似た道具が無いわけではありません。調べた範囲では、Claude CodeとCodexの履歴を繋ぐ codex-claude-relay というOSSがあり、作りは近いのに、見つけた時点ではGitHubのStarが0でした。エージェント同士のhandoffツールも複数あります。ただどれも開発者向けの文脈で語られていて、「引き継ぎ書を書きたくない」という素朴な動機から出発したものは見当たりませんでした。

## 抜けていた場所

ここまでで、Macの上のClaude CodeとCodexは繋がりました。抜けていたのはスマホです。

電車の中でClaudeアプリと話していて、いいところまで進むことがあります。記事の構成とか、設計の相談とか。家に帰ってMacで続きをやろうとすると、その会話はスマホのClaudeの中にしかない。Macの記録には存在しないので、relayでは読めません。結局、会話を自分でコピペして運ぶことになります。

以前これを別の方法で解決しようとして、10手かかりました。Macを起こして、設定を開いて、AirDropして、メモに貼って、スマホで全選択して。やり終えたあとの感想は「めちゃくちゃめんどかった」の一言です。

今回作ったのは投函口です。スマホのClaudeに「この会話をrelayに預けて」と言うと、会話が自分のMacに届く。それだけの穴を、安全に開けます。

## 穴の開け方

構成はこうなりました。

```text
スマホのClaude
  → Cloudflare Access（本人確認の門番）
  → Cloudflare Tunnel（Macへの土管）
  → 投函専用MCPサーバー（Macの127.0.0.1でだけ動く）
  → ~/.local/share/session-relay/inbox/
```

Claudeのカスタムコネクタは、公開URLのMCPサーバーを登録できて、スマホアプリからも使えます。なのでMac側のMCPサーバーをCloudflare Tunnelで外に出し、Cloudflare Accessで自分のメールアドレスだけを通す。認証はAccessのManaged OAuthに任せたので、OAuthの自作はしていません。

設計で決めていたのは2つです。

ひとつ、外に見せる道具は deposit_conversation の1つだけ。預ける方向しかありません。ローカルの会話履歴を読む道具は外向きのMCPには載せない。仮に認証を破られても、できることは私の受信箱にゴミを入れることだけです。

ふたつ、門番を信用しすぎない。Accessを通ったかどうかは、Cloudflareが付けてくる署名付きJWTをMac側でも公開鍵から検証します。issuerとaudienceまで見ます。トンネルの設定をミスって認証なしで公開してしまっても、MCP本体が拒否する二段構えです。

この二段目、保険のつもりでしたが、初日に仕事をしました。AccessのアプリケーションにSubdomainを入れ忘れていて、門番が立っていない時間があったんです。外から叩いたら、Cloudflareを素通りしてMacまで届いていました。返ってきたのは私のサーバーの403、「Cloudflare Access JWT is required」。設定ミスは起きるものだと思って作っておいてよかったです。

費用は、ドメイン代の年10.46ドルだけでした。Cloudflare TunnelもAccessも、個人利用の範囲は無料枠に収まっています。ドメインを持っていなかったので今回買いましたが、これは投函口専用ではなく、今後の公開物すべての土台になります。

## 実機で通した

まずWeb版のClaudeで、接続テスト用の合成データを投函しました。Macに届いたJSONの中身、権限、sourceの値を確認。次にiPhoneのClaudeアプリで、本物の会話から「この会話をrelayに預けて」。届きました。source は claude-mobile、私の発話と直近の経過が原文のまま入っていました。

拒否側も確認しています。認証なしで公開URLを叩くと401。署名なしのリクエストはMac側で403。偽のHostヘッダーも403。受信箱はディレクトリ0700、ファイル0600で、入力は1件64KB、会話全体256KBまでに制限しています。

これで、電車で考えたことが家のMacの続きになりました。方向は片道です。スマホからMacへは預けられますが、Macの会話をスマホのClaudeアプリへ流し込む口はありません。Mac側のClaude CodeとCodexの間は、前からどちら向きにも移れます。

再現手順は [docs/remote-mcp-ja.md](https://github.com/shoujiki-panman/session-relay/blob/main/docs/remote-mcp-ja.md) に置きました。共有サーバーは運営していません。使う人が自分のCloudflareアカウントと自分のMacに、自分専用の投函口を建てる形です。会話は他人のサーバーに置かない、という線は最初から変えていません。

## 作ってみて分かったこと

テストが緑でも、道具は平気で役に立ちません。会話の一覧機能を作って、テストが全部緑になったあとに実際の画面へ出したら、15本中6本の見出しがスクリーンショットのファイルパスでした。そのとき打った感想がそのまま残っています。「これだとわからんな。。。」。別の日には、一覧87本のうち50本以上が自動実行の残骸だったこともあります。除外の規則は、実データを画面に並べて初めて足りないと分かる。この繰り返しでした。

いちばん効いた設計判断は、たぶん機能ではなく態度です。途中で、AIが「番号かrefを言ってください」と聞き返してくる問題がありました。コマンドを打ちたくない人にIDを言わせるのは、コマンドを打たせているのと同じです。なので道具の説明文に「refを本人に聞き返すな」と書きました。以来、冒頭のスクショ貼りのような雑な渡し方でも、AIが候補を絞って勝手に見つけてきます。

npmでの配布は済ませ（`npm install -g @shoujiki-panman/session-relay` で入ります）、投函口はlaunchdで常駐にして、Macを再起動しても勝手に開き直すようにしました。残りの細かい課題はGitHubのIssueに並べてあります。壊れても困るのは私だけ、というのがセルフホストのいいところでもあります。

## まとめ

- 引き継ぎ書はもう書かない。自分が打った言葉の原文だけを、次のチャットへそのまま運ぶ
- 使い方は、新しいチャットに「続きから」と言うか、止まった画面のスクショを貼るだけ
- Claude Code⇄Codexは行き来自由。スマホのClaudeの会話も「預けて」と言えばMacに届く（ここだけCloudflareの設定が要る）
- 会話の保存先は自分のMacだけ。共有サーバーはない

```sh
npm install -g @shoujiki-panman/session-relay
relay install   # MCPと「続きから」スキルをまとめて登録
relay doctor    # 登録と生存の検査。繋がらない時もまずこれ
```
